# Hit@3
前 3 个结果里，是否至少有一个是正例
hit_at_3 = 1 if any(t in positive_titles for t in top3) else 0
衡量"有没有结果能用"。1.000 = 每次检索 Top3 至少命中一篇相关攻略。

# Precision@5
Top-5 里正例占的比例，分母固定为 5
p5 = n_correct / 5   # n_correct = top5中有几个是positive_titles
现在你的 positive_titles 补到了 3-5 个，这个指标的理论上限从 32.5% 升到了 60-100%，P@5 也从 .25 跳到了 .56，不再被标注稀疏性压制。

# Recall@5
标注的正例里，Top-5 找回了几分之几

```
r5 = n_correct / len(positive_titles)
```
衡量"找全了没"。.635 意味着标注的 3-5 个正例中，Top-5 平均找回了约 63.5%。

# MRR@5
第一个正例排在第几位，取倒数

- 如果第一个正例排在第1位 → 1/1 = 1.0
- 如果第一个正例排在第3位 → 1/3 = 0.333
- 如果前5没有正例 → 0
衡量排名质量。.955 = 正例几乎总在 Top1-2。

# City@5
Top-5 里去重后，城市正确的比例
city_match = sum(city == expected_city for c in top5_cities) / 5
衡量"会不会串城"。.990 = 几乎不会把成都攻略推荐给杭州用户。

# Section@5
Top-5 chunk 的段落类型是否匹配查询期望的类型
```
raw: 基于未去重的 raw_results[:5]
guide: 基于去重后的 deduped_results[:5]
matched = sum(s in expected_sections for s in chunk_section_types) / 5
```
.query 问"交通怎么走"，期望 section_type 是 transport，返回的 chunk 如果主要是 food 就不对。.567 = 超过一半的 chunk 段落类型匹配。

# Must@1
标注的"最佳攻略"是否排在第 1 位


must_hit_at_1 = 1 if top5[0] == must_title else 0
最硬核的单点指标。.651 = 65% 的查询，最该出现的那篇攻略确实排在第一。

# Top1+
Top-1 的标题是否在正例列表中
top1_positive = 1 if top5[0] in positive_titles else 0
比 Must@1 宽松——不需要是最佳那篇，只要是正例就行。.928 = 92.8% 的情况下第一条结果就是对的。

# Neg@5
Top-5 里混入了几个负例
neg = sum(t in negative_titles for t in top5) / 5
衡量"会不会推错"。.005 = 几乎零污染。
