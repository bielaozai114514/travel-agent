# RCC-TP 算法实验报告

## 基于攻略候选约束的阶段式行程规划算法

---

## 1. 算法概述

### 1.1 问题定义

传统旅游行程规划中，大语言模型（LLM）通常从城市级完整景点空间中自由选择景点生成行程。这种方式存在两个问题：

1. **候选空间过大**：LLM 需要在数十个城市地标中做出选择，容易产生不合理组合（如跨区域远距离景点同日安排）
2. **缺乏个性化约束**：LLM 无法直接感知用户的偏好上下文与攻略知识中的经验约束

**RCC-TP（RAG-Candidate Constrained Trip Planning）** 在 LLM 生成行程之前，利用 RAG 检索结果对候选景点和住宿区域进行预筛选，将城市级全量地标压缩为个性化候选集合，以此约束后续的地图搜索和行程生成过程。

### 1.2 核心思想

> 不是让 LLM 在城市全量景点空间中自由生成行程，而是先用 RAG 从攻略知识库中检索出与用户需求相关的候选景点和住宿区域，再用这些候选项约束地图搜索的范围和 LLM 的规划空间。

### 1.3 算法流程

```
输入: 用户请求 r, 攻略知识库 D, 地图服务 M
输出: 结构化行程 P

1.  q ← BuildRAGQuery(r)                     // 构造 RAG 查询
2.  G ← AdaptiveTCRRAG(q, D)                 // M5 自适应旅游约束检索
3.  C_attr, C_area ← ExtractCandidates(G)    // 从攻略结果抽取候选景点/区域
4.  A ← SearchAttractions(M, C_attr)         // 候选景点驱动的地图搜索
5.  H ← SearchHotels(M, C_area)              // 候选区域驱动的酒店搜索
6.  W ← QueryWeather(r.city)                 // 天气查询
7.  P_raw ← LLM_Generate(r, G, C_attr, C_area, A, H, W)  // 候选约束下的行程生成
8.  P ← NormalizeFixLocation(P_raw)          // 标准化与坐标修正
9.  return P
```

核心创新点在于步骤 3-4：**候选抽取作为 RAG 检索与地图搜索之间的桥梁**。传统的"城市→地图搜索→LLM 生成"管道被替换为"RAG 检索→候选抽取→定向地图搜索→候选约束 LLM 生成"。

### 1.5 候选抽取算法详解

候选抽取（`extract_candidates_from_guides`）是一个**纯规则、零 LLM 调用**的子模块：

```
输入: RAG 检索结果列表 G, 目标城市 city
输出: 候选景点列表 C_attr (≤8个), 候选区域列表 C_area (≤5个)

1. 加载城市扩展地标词典 L = EXTENDED_LANDMARKS[city]
2. 加载城市区域关键词词典 A = AREA_KEYWORDS[city]
3. 初始化 attraction_counter, area_counter
4. FOR each result in G:
     a. 遍历 L, 若地标名称出现在结果文本中 → attraction_counter[地标] += 1
     b. 遍历 A, 若区域关键词出现在结果文本中 → area_counter[区域] += 1
     c. 从 tags 提取偏好标签
     d. 从 section_type="tip" 的 chunk 提取避坑提示
5. 从候选景点反推区域（通过 ATTRACTION_AREA_MAP 映射）
6. C_attr ← 按出现频次降序取前 MAX_CANDIDATE_ATTRACTIONS(8) 个
7. C_area ← 稳定排序（频次降序 → 预定义顺序 → 字典序）取前 MAX_CANDIDATE_AREAS(5) 个
8. RETURN C_attr, C_area
```

## 2. 实验设置

### 2.1 实验数据

实验数据来自系统生成的 30 条初始行程（`trip_initial_plans.jsonl`），覆盖 5 个旅游城市，包含 1/2/3/4/5 天不同行程长度和多种旅行偏好（老人轻松游、亲子游、美食游、历史文化游、情侣游、综合游等）。

**数据来源说明**：30 条初始行程由 `TripPlannerAgent` 在 `TRIP_RISK_REPAIR_ENABLED=false` 环境下生成（关闭风险修复以避免数据污染），每条记录包含完整的 `request`（用户请求）、`candidate_attractions`（RAG 抽取的候选景点）、`candidate_areas`（RAG 抽取的候选区域）和 `initial_plan`（LLM 生成的最终行程）。

### 2.2 数据集统计

| 统计项 | 值 |
|--------|-----|
| 总样本数 | 30 |
| 覆盖城市 | 杭州、成都、北京、西安、厦门（各6条） |
| 行程天数分布 | 2天(5条)、3天(21条)、4天(1条)、5天(3条) |
| 偏好类型 | 老人轻松游、亲子美食、历史文化、美食游、情侣游、综合游 |

### 2.3 评估指标

| 指标 | 定义 | 含义 |
|------|------|------|
| **平均候选数** | 每条行程的候选景点数量均值 | 候选空间的规模 |
| **候选压缩率** | 平均候选数 / 城市完整地标数 | 相对城市全量地标的压缩程度 |
| **规划景点支持率** | 被候选集覆盖的最终规划景点比例 | 候选项对最终规划的约束能力 |
| **候选利用率** | 至少被一条行程使用的候选景点占全部候选的比例 | 候选集合的信号精度 |

### 2.4 对比基线

| 方法 | 候选集来源 | 机制 |
|------|-----------|------|
| **UserText** | 从用户输入自由文本中显式提取景点名称 | 纯用户驱动，无知识库辅助 |
| **CityDict** | 使用城市完整扩展地标词典作为候选集 | 城市级全量空间，无个性化 |
| **RCC-TP（本算法）** | 基于 RAG 检索结果抽取攻略中高频出现的景点 | 攻略知识驱动的个性化候选约束 |

## 3. 实验结果

### 3.1 主实验：三种候选策略对比

| 候选策略 | 平均候选数 | 候选压缩率 | 规划景点支持率 |
|----------|----------:|----------:|------------:|
| UserText（用户输入显式景点） | 1.10 | 7.14% | 14.42% |
| CityDict（城市完整地标词典） | 15.40 | 100.00% | 94.42% |
| **RCC-TP（本算法）** | **7.57** | **49.13%** | **89.30%** |

**核心发现**：

- **UserText**：用户自由输入中平均仅提及 1.10 个具体景点，只能覆盖最终行程 14.42% 的景点。大量用户需求是隐式的（如"不想太累"、"历史文化游"），无法直接映射为具体景点名。
- **CityDict**：城市全量地标词典覆盖率最高（94.42%），但候选空间过大（15.40 个），缺乏个性化约束，LLM 仍需在大量候选间自行判断。
- **RCC-TP**：在候选规模压缩至城市全量 **49.13%**（约一半）的前提下，仍保持 **89.30%** 的规划景点支持率，仅比城市全量低 5.12 个百分点。

### 3.2 按城市分组分析

| 城市 | 样本数 | 城市地标数 | 唯一候选景点数 | 候选占用比 | 候选支持率 | 地标支持率 |
|------|:----:|:--------:|:------------:|:--------:|:--------:|:--------:|
| 杭州 | 6 | 18 | 9 | 50.0% | 95.00% | 97.50% |
| 成都 | 6 | 16 | 10 | 62.5% | 89.47% | 94.74% |
| 北京 | 6 | 17 | 11 | 64.7% | 91.84% | 95.92% |
| 西安 | 6 | 15 | 9 | 60.0% | 90.91% | 100.00% |
| 厦门 | 6 | 11 | 6 | 54.5% | 79.55% | 84.09% |
| **平均** | — | **15.40** | **9.00** | **58.34%** | **89.30%** | **94.42%** |

**分析**：

1. 各城市唯一候选景点占用比在 **50%–65%** 之间，说明 RAG 候选抽取具有城市适应性——不同城市的地标丰富度不同，但候选集始终聚焦于攻略中高频出现的核心景点。
2. 厦门表现相对偏低（候选支持率 79.55%），原因是厦门地标库仅 11 个（5 城中最少），且部分行程中的景点（如小众餐饮店铺）不在城市地标库中，导致 RAG 候选抽取无法命中。
3. 西安地标支持率达到 100%，说明 RAG 检索结果完美覆盖了该城市所有历史行程中出现过的景点类型。

### 3.3 按行程天数分组分析

| 行程天数 | 样本数 | 平均候选数 | 平均规划景点 | 候选支持率 |
|:------:|:----:|:--------:|:---------:|:--------:|
| 2天 | 5 | 7.60 | 5.80 | 100.00% |
| 3天 | 21 | 7.52 | 7.19 | 87.42% |
| 4天 | 1 | 8.00 | 8.00 | 100.00% |
| 5天 | 3 | 8.00 | 9.00 | 85.19% |

**分析**：

- 2 天短行程候选支持率 100%，因为景点数少（平均 5.8 个），候选集（平均 7.6 个）完全覆盖。
- 5 天长行程候选支持率降至 85.19%，因为行程越长，LLM 需要填充的景点越多，越可能超出攻略高频景点的范围。
- 候选集大小（7.5–8.0）不随行程天数变化，受 `MAX_CANDIDATE_ATTRACTIONS=8` 上限约束。这说明当前候选规模在不同天数下具有一致的约束强度。

### 3.4 候选利用率分析

| 指标 | 值 |
|------|----|
| 30 条行程候选景点总出现次数 | 227 次 |
| 至少被一条行程使用的去重候选数 | 192 次 |
| **候选利用率** | **84.58%** |
| 未被使用的候选比例 | 15.42% |

候选利用率 84.58% 说明 RAG 抽取的候选景点**信号精度高**——超过五分之四的候选项确实在后续某条行程中被 LLM 实际选用，仅有约 15% 的候选未被任何行程采纳。

## 4. 消融分析（与预约束变体对比）

为了进一步验证 RCC-TP 中"RAG 候选约束"这一环节的独立贡献，可以构造以下消融变体：

| 变体 | 候选来源 | 约束方式 |
|------|---------|---------|
| **NoConstraint** | 不使用候选，LLM 自由生成 | 无候选注入，prompt 中删除候选景点/区域字段 |
| **RCC-TP（本算法）** | RAG 候选抽取 | 候选景点+候选区域注入 prompt |

消融对比建议关注的维度：
- **规划景点候选支持率**：NoConstraint 下该指标退化为城市地标支持率
- **候选驱动的搜索精度**：RCC-TP 下景点搜索从城市级泛搜索变为候选景点定向搜索
- **规划结构合理性**：通过后续风险评分（RC-LRA 风险分）间接衡量候选约束对行程质量的影响

---

## 5. 实验结论

1. **RCC-TP 的候选压缩与支持率之间存在良好平衡**：在将城市全量地标压缩 50.87% 的同时，保持了 89.30% 的规划景点支持率，仅比全量地标低 5.12 个百分点。

2. **相比用户显式输入**，RCC-TP 将候选空间从 1.10 个景点扩展至 7.57 个，支持率从 14.42% 提升至 89.30%，证明攻略知识库能有效补充用户隐式需求。

3. **相比城市全量地标**，RCC-TP 将候选空间从 15.40 压缩至 7.57（压缩率 49.13%），使 LLM 的规划空间更具针对性，同时保留了接近的覆盖能力。

4. **候选利用率 84.58%** 表明 RAG 候选抽取的信号精度高，大部分候选确实被 LLM 在行程生成中实际使用。

5. **城市适应性**：RCC-TP 在不同城市间的候选占用比稳定在 50%-65%，说明算法具有跨城市泛化能力。

```

   ↓

```
