# 旅游行程规划 Agent

把旅行社顾问的行程规划流程做成可复用的 Agent：一句自然语言需求 → 结构化行程单（含动线、餐饮、预算）。

> 背景：定制游的行程规划高度依赖顾问个人经验，一份 5–7 天行程平均耗时 2–3 小时，旺季响应不及时直接导致询单流失。本项目的目标是把「需求澄清 → 行程编排 → 预算核算」这条链路自动化，让人只做最后的复核与微调。

## 一、它解决什么问题

| 环节 | 人工做法 | 本项目的做法 |
|---|---|---|
| 需求澄清 | 顾问电话/微信反复问目的地、天数、预算、同行人 | 一次自然语言输入解析成结构化参数，缺参数自动补默认值并标注 |
| 行程编排 | 凭经验挑景点，容易跨城折返 | 按**片区聚类**排程，同一天的景点尽量落在同一片区域 |
| 预算核算 | Excel 手算，易漏项 | 门票 / 餐饮 / 住宿 / 市内交通分项核算，与用户预算自动对照 |
| 输出 | Word 手写行程单 | 结构化 JSON + 可直接发送的 Markdown 行程单 |

## 二、架构

```
用户输入（自然语言）
      │
      ▼
┌─────────────────┐
│ 意图解析 Agent   │  LLM 结构化抽取 ──失败/无Key──▶ 规则引擎兜底
│ intent.py       │  输出：city / days / budget / people / pace
└────────┬────────┘
         ▼
┌─────────────────┐
│ 景点工具层       │  按城市 + 人群召回候选，按片区聚类
│ tools/attractions│  （当前读本地库，可替换为高德 POI / MCP）
└────────┬────────┘
         ▼
┌─────────────────┐
│ 行程编排 Agent   │  片区聚类 → 每日分桶 → 时间轴编排 → 预算核算
│ planner.py      │  固定骨架：09:00 起 → 12:00 午餐 → 13:00 下午 → 18:00 晚餐
└────────┬────────┘
         ▼
   结构化 JSON + Markdown 行程单
```

### 三个关键设计

1. **双引擎可降级**：有模型 Key 走 LLM 抽取，无 Key 或调用失败自动落回规则引擎（城市词表 + 中文数字解析 + 人群关键词）。保证演示环境永远可用，也让评测结果不受模型波动影响。
2. **片区聚类优先于数量**：宁可一天排 2 个同片区景点，也不跨城凑 3 个。片区聚类率从 46.9% 提到 81.9%（见评测）。
3. **时间轴固定骨架**：上午/下午两个时段按容量分配景点，午餐 12:00、晚餐 18:00 固定，避免出现时间倒挂——这是第一版最主要的 bug。

## 三、评测

30 条标注用例（`data/eval_cases.jsonl`），覆盖 5 个城市 × 亲子/老年/情侣/商务/独自 5 类人群 × 3 种节奏。

```bash
python scripts/eval.py                 # 全量
python scripts/eval.py --limit 5       # 快速验证
python scripts/eval.py --json out.json # 落盘，用于改前改后对比
```

### 指标定义

| 指标 | 定义 |
|---|---|
| 意图字段准确率 | city / days / people / pace 四项逐条比对，任一错即该条记错 |
| 行程结构通过率 | 天数正确 + 每天至少 1 个景点 + 每天含午晚餐 |
| 约束满足率 | 无重复景点 + 时间轴递增 + 每天景点数不超过节奏上限 |
| 片区聚类率 | 同一天所有景点落在同一片区的比例（衡量动线合理性） |

### 迭代记录

| 版本 | 意图准确率 | 结构通过率 | 片区聚类率 | 主要改动 |
|---|---|---|---|---|
| v1 | 100%* | 30.0% | 100%* | 时间轴按「跨过饭点才插入」动态计算，导致晚餐时间早于景点结束 |
| v2 | 100%* | 60.0% | 43.6% | 改为固定骨架（上午/午餐/下午/晚餐），修复时间倒挂；暴露出景点库数量不足 |
| v3 | 100%* | 93.3% | 46.9% | 扩充景点库至 12–13 个/城市，修复天数缺失 |
| v4 | 100%* | **100%** | 46.9% → **81.9%** | 片区优先策略：同片区不足时才跨区补到下限 2 个 |
| v5 | **86.7%** | 100% | 81.9% | 接入真实 LLM；同时修正评测集中 4 条被标注错的 `pace` |

\* v1–v4 的「100%」是**评测集过拟合**：这些标注是照着规则引擎的关键词拍的，规则引擎必然全对。v5 修正标注后掉到 86.7%，才是真实水平。

**结构层的两条结论**：结构通过率 30% → 100% 靠「把时间轴从动态计算改成固定骨架」；聚类率 46.9% → 81.9% 靠「宁可少排一个景点，也不跨城凑数」。两者都不涉及模型，纯规则层优化。

### 双引擎对比（规则引擎 vs LLM）

```bash
python scripts/eval.py --engine rule --json out/eval_rule.json
python scripts/eval.py --engine llm  --json out/eval_llm.json
python scripts/compare.py out/eval_rule.json out/eval_llm.json
```

| 指标 | 规则引擎 | LLM | 差值 |
|---|---|---|---|
| 意图字段准确率 | 86.7% | 86.7% | +0.0% |
| 行程结构通过率 | 100.0% | 100.0% | +0.0% |
| 片区聚类率 | 81.9% | 78.6% | -3.3% |

**结论（反直觉但重要）**：两者准确率相同，但**错的不是同一条**——共同错误 3 条，各自独有错误各 1 条（Jaccard 相似度 0.6）。

- 共同错误的 3 条都是「抽空看看 / 顺便逛逛 / 边玩边学」这类**隐含节奏**的表达，两种方法都没抓到；
- 差异项上各有胜负：`中间有半天时间逛逛` 规则引擎对、LLM 判成 relaxed；`只有晚上有空` 反而 LLM 对、规则引擎判成 normal。

所以「接 LLM 一定更好」在这个任务上**不成立**。LLM 的真实价值不在准确率，而在它能把「过个周末」推断成 2 天（规则引擎只会默认 3 天），以及能处理词表外的表达。

### 这个评测集的局限（必须说明）

1. **样本只有 30 条**，单条权重 3.3%，统计意义弱，1–2 条的波动不足以证明优劣；
2. **`pace` 是主观维度**：「出差抽空逛逛」算 relaxed 还是 normal，不同人标注会不一样。更合理的做法是不评测 pace，而是评测**可观测的结果**（每天景点数、单日总时长）——这是我下一步要改的；
3. **标注最初是按规则引擎调的**，v1–v4 的高分有系统性偏差，v5 修正后才可比。

## 四、快速开始

```bash
pip install -r requirements.txt
cp .env.example .env      # 填入自己的 Key；不填则走规则引擎

uvicorn app.main:app --reload --port 8000
```

支持任意 OpenAI 兼容接口（DeepSeek / 通义 / 硅基流动 / 自建中转站），只需改 `.env` 里的 `LLM_BASE_URL` 与 `LLM_MODEL`。

打开 http://127.0.0.1:8000 是演示页，接口：

```bash
curl -X POST localhost:8000/plan -H "Content-Type: application/json" \
  -d '{"text":"带父母去杭州玩三天，路线轻松一点，预算五千"}'
```

## 五、已知限制 / 下一步

- 景点库为本地示例数据，尚未接入高德 POI 实时数据（接口层已按 POI 字段对齐，替换只需改 `tools/attractions.py`）
- 未考虑营业时间与预约制（如故宫周一闭馆、厦大需预约），当前只在行程单里以备注形式提示
- 未做多轮修改：目前一次生成，不支持「把第二天换成博物馆」这类指令
- 未接入交通耗时：片区聚类只是近似，真实动线需要路径规划 API
